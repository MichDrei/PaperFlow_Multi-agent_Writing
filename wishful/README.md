# 许愿式编程 · 四个小案例

> 先把"如果世上已经有这东西，我会怎么用它"写下来，
> 再让实现去追那行调用。

许愿式编程（wishful programming）不是某种框架，而是一种写代码的顺序：**调用点先行**。
你假想自己已经拥有完美的 API，用它把问题解决一遍；这行"愿望"就是最严格的需求文档，
接下来所有实现都只为让它成真。

它和 TDD 同源（愿望常写成断言），但重心不同：TDD 关心"对不对"，许愿式关心"用起来顺不顺"。
愿望写得越具体、越短、越像人话，实现的方向就越清楚。

运行：

```bash
python3 wishful/wishes.py
```

四个案例都在这一个文件里，每个都先给愿望，再给兑现愿望的最小机器。

---

## 案例 1 · 计算器：愿望是一个能读懂算式的函数

```python
calc("1 + 2 * 3")        == 7
calc("(1 + 2) * 3")      == 9
calc("2 * (3 + 4) - 5")  == 9
calc("-3 + 10 / 4")      == -0.5
```

愿望里其实已经藏着文法：`算式 → 项 → 因子 → 数字 | ( 算式 )`。
所以实现几乎是照抄：一个只有三个方法的递归下降解析器，每个方法对着愿望里的一行。

```python
def expr(self):          # 算式 := 项 (('+' | '-') 项)*
    value = self.term()
    while self.peek() in ("+", "-"):
        op = self.eat()
        rhs = self.term()
        value = value + rhs if op == "+" else value - rhs
    return value
```

**看点**：愿望规定了"调用长什么样"，文法规定了"实现长什么样"，两者是同一棵树的两种写法。

## 案例 2 · 素数：愿望是一条取之不尽的数列

```python
PRIMES.take(8)          == [2, 3, 5, 7, 11, 13, 17, 19]
PRIMES.nth(100)         == 547
PRIMES.map(sq).take(4)  == [4, 9, 25, 49]
```

存在无穷多个素数，所以"取之不尽"在这里不是修辞，是事实。
愿望要求一个**惰性且带缓存**的流：取到才算，算过就记住（否则第二次 `.take` 会从头再筛一遍）。

```python
class Stream:
    def __iter__(self):
        i = 0
        while True:
            if i < len(self._cache):          # 算过的直接给
                yield self._cache[i]
            else:                             # 没算过的才算
                ...
                self._cache.append(value)
                yield value
            i += 1
```

有了它，埃氏筛可以写得几乎和它的定义一样：

```python
def _sieve(s):
    p = next(iter(s))                      # 第一个数一定是素数
    rest = s.filter(lambda n: n % p)       # 剩下的倍数全部扔掉
    return Stream(lambda: chain([p], _sieve(rest)))
```

**看点**：愿望里的"无穷"能被兑现，是因为实现把"什么时候算"和"算多少"拆开了。

## 案例 3 · 查询：愿望是说人话

```python
Query(USERS)
    .where(lambda u: u.age >= 30)
    .order_by("age", desc=True)
    .pick("name", "age")
    .limit(3)
    .all()
```

每一环都返回**新的、不可变的** `Query`，所以链上任何一段都能单独拿出来读、单独测试。
`where` 里用 `u.age` 而不是 `u["age"]`，靠一行 `__getattr__ = dict.__getitem__` 实现——
愿望里多写一个 `u.age`，实现就多写这一行，很划算。

**看点**：链式 API 的美感来自"每步都是完整结果"，而不是来自省略了几个中间变量。

## 案例 4 · 表格：愿望是一张会自己重算的纸

```python
sheet["小计"] = lambda s: s["单价"] * s["数量"]
sheet["折扣"] = lambda s: 0.9 if s["小计"] > 250 else 1.0
sheet["总价"] = lambda s: round(s["小计"] * s["折扣"], 2)
```

改一个格子，整张表自动跟着变——依赖关系由求值顺序自动决定，不用手写重算逻辑：

```python
class Sheet(dict):
    def __getitem__(self, key):
        value = super().__getitem__(key)
        return value(self) if callable(value) else value
```

**看点**：三个字的 `__getitem__` 撑起了整个"响应式"错觉。愿望越像常识，实现往往越短。

## 许愿的三条纪律

1. **愿望要能跑。** 写成可执行的调用或断言，而不是伪代码或注释。
   `calc("1 + 2 * 3") == 7` 是愿望，`// 解析表达式` 不是。
2. **愿望要短。** 一行调用读不顺，说明 API 还没想清楚，别急着实现。
   先把调用删到只剩名词和动词。
3. **愿望要能兑现。** 许愿是压缩需求，不是逃避工程量。解析器该有的状态、流该有的缓存、
   查询该有的排序，一样都少不了——只是现在它们被精确地放在了该在的位置。

## 什么时候别许愿

- **需求还不稳定时**：愿望会变成沉没成本，改一次调用要改整条链。
- **性能是核心指标时**：链式 API 和惰性流都带着一层抽象，热点路径上要先量再许。
- **团队不熟这套语汇时**：一个只有作者读得懂的"漂亮调用"，不如三段朴素循环。

许愿式编程最值钱的地方，是它把**设计压力提前**了：在你写第一行实现之前，
你就得回答"这东西用起来该是什么样"。答案一旦落笔，实现通常只剩体力活。
